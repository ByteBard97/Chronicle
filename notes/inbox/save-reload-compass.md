# External-State Sync for Skyrim SE/AE: How AI-NPC Mods Handle Save/Load/Reload Consistency, and a Recommended Protocol

## TL;DR
- **No mainstream Skyrim AI-mod solves reload consistency cleanly; they mostly *ignore* it and drift, except CHIM, which does timestamp-based reconciliation and forks a snapshot into its Playthrough Manager rather than rolling back.** Mantella persists per-NPC conversation summaries as flat files keyed by player name, so a reload silently keeps "future" memories; SkyrimNet keeps an in-process store read straight from game memory with no per-save fork.
- **The correct primitive is a save-embedded identity written through SKSE's SerializationInterface co-save**, which is created, deleted, and renamed in lockstep with the `.ess`. CHIM only approximates timeline identity via Skyrim's internal clock (`gamets`, seeded at 10,000,000 on save creation); a stored UUID + monotonic counter is strictly stronger.
- **Recommended: treat your Python service as an event-sourced store keyed by a `(save_uuid, generation_counter)` timeline id embedded in the co-save; on load, compare the loaded save's watermark against your log head and fork a new branch when it is in the past — never destructively roll back.** Handle the `OnPlayerLoadGame`/`kPostLoadGame` race by requiring the game to push its watermark before the service commits any new events.

## Key Findings

1. **Reconciliation behavior differs sharply across the three mods.** CHIM/HerikaServer is the only one with an explicit reload story: it stores every event in a server-side database tagged with Skyrim's internal game clock and, when you load an older save, detects the backward jump and deletes "future" events, snapshotting them first (the "Playthrough Manager"). Mantella stores per-NPC conversation summaries as flat text/JSON files under `Documents/My Games/Mantella/data/Skyrim/conversations/<PlayerName>/` and has no reload reconciliation — reloading an earlier save leaves later summaries in place (drift/corruption of the narrative). SkyrimNet is in-process (a DLL reading game memory directly with a vector DB) and explicitly avoids serialization round-trips, so it has no cross-process save-fork mechanism at all.

2. **SKSE's SerializationInterface is the atomic anchor.** The co-save (`.skse`) is written, deleted, and renamed alongside the `.ess`; on load the callback order is `kPreLoadGame` → Revert → Load → `kPostLoadGame`, where Revert wipes stale in-memory state before Load repopulates it. This is the standard way to keep plugin state atomic with the save — and the natural place to embed a per-save identity that an external process can read.

3. **A save-embedded UUID is a sound but under-used pattern in Skyrim specifically.** The GUID-on-start + heartbeat approach to detect reloads is documented in other engines (e.g., the "realms" NWN module), but Skyrim mods more commonly reconcile via timestamps (CHIM's `gamets`) than via a stored GUID. Nothing prevents you from doing the stronger thing.

4. **Real race conditions exist between load completion and external notification.** `OnPlayerLoadGame` does not fire on a brand-new game, and `kPostLoadGame` can fire before the Papyrus VM/forms are fully ready — so an external service must not assume "load done" equals "game ready."

## Details

### (1) How Mantella, CHIM/HerikaServer, and SkyrimNet reconcile external memory on reload/death/multi-save

**Mantella — ignore (and drift).** Mantella's architecture deliberately keeps state minimal in-engine: "Dialogue replacement, not logic replacement... Papyrus handles state... no persistent save changes." Its long-term memory is a set of per-NPC summary files. From v0.12 these live in `Documents/My Games/Mantella/data/Skyrim/conversations/YourPlayerName1/`; per Mantella's official Skyrim Installation docs, "When a conversation ends, a summary of the conversation is saved to a local text file for each NPC... These summaries are then loaded the next time an NPC is spoken with. You can view / edit these summaries in your My Games/Mantella/data/Skyrim/conversations/YourPlayerName1/ folder." Crucially the folder is keyed by player name with a trailing index (`YourPlayerName1`), not by save file or timeline. There is no hook that rolls back or forks these files when you reload an earlier save or die — so a reload leaves "future" summaries intact, and multiple characters sharing a name collide. Community forks confirm this is a known weak point: Pantella "has a completely new memory system that depreciates the old summary memory" using ChromaDB because summaries are "lossy." Mantella also moved from file-based IPC to HTTP ("Road to v0.12: Using HTTP to communicate with game"), but that changed transport, not reload semantics. Net verdict: **ignore → silent drift/corruption of narrative memory across reloads and across same-named characters.**

**CHIM/HerikaServer — reconcile by timestamp, fork a snapshot.** CHIM keeps a heavyweight server-side store (PostgreSQL for events/profiles; ChromaDB for vector "TXT2VEC" memories) inside a WSL Debian VM ("DwemerDistro"). Every in-game event is logged with timestamps. Per the HerikaServer source, the fields are: "gamets: skyrim internal time. starts at 10'000'000 on save game creation. localts: unix timestamp of the server. ts: ... coming from Skyrim." The event log is ordered by `gamets`, so Skyrim's internal clock is the primary ordering key. Because the server DB persists independently of the `.ess`, loading an older save makes `gamets` jump backwards relative to what the server already recorded. CHIM detects this and, per its own FAQ, "Due to how we track ingame time and events to sync with the server, we have to delete events that have happened in the 'future'. They should be saved in the playthrough manager." The Nexus changelog describes it as "Playthrough Manager (Beta) - Auto backup events when loading very old saves," and the docs frame the trigger with the lore-flavored "DragonBreak." So CHIM's model is: **detect backward time jump → snapshot ("fork") the diverging events/memories into the Playthrough Manager → delete the future events from the active timeline → optionally restore a snapshot manually.** This is closer to *fork + prune* than to rollback, and it is per-server-global rather than per-save-slot, which is why multi-character play requires the separate backup/restore "Playthrough Manager Scripts" to swap CHIM profile sets between Skyrim playthroughs. CHIM also added an "Individual memory bank" option (per-NPC memory instead of the global shared one), which changes granularity but not the reconciliation model. Known failure mode: a corrupted `conf.php` breaks the sync/time tracking and must be regenerated.

**SkyrimNet — in-process, no cross-process fork.** SkyrimNet is explicitly designed against the external-server approach. Its docs Overview states: "Unlike other AI projects that take an external server approach, SkyrimNet uses an in-process design as a DLL without requiring WSL or external servers." Its README elaborates: "It is a native Windows DLL that loads inside Skyrim itself... Game state is read straight from memory (no syncing, no serialization round-trips between processes)." Memory is created "with full vector embeddings" and surfaced through lifecycle ModEvents (`SkyrimNet_MemoryCreated`, `SkyrimNet_DiaryCreated`). Because it reads live memory rather than reconciling an external store against the save, it has no explicit rollback/fork logic for reloads; its consistency is only as good as what it persists and re-reads per load, and its recent fixes concern deduplication of "Knowledge Keys," not timeline forking. It has documented load-timing stress ("SkyrimNet cannot keep up with game load"), which is itself a race-condition signal (see §4). Net verdict: **effectively ignore/implicit**, relying on in-process proximity rather than an explicit sync protocol.

**Bottom line for (1):** Only CHIM treats reload as a first-class event, and even it does so globally (not per-slot) and destructively-with-backup. None of the three implement true per-timeline branching keyed to a save identity — which is exactly the gap your service should fill.

### (2) SKSE co-save serialization (SerializationInterface)

**What it is and what it stores.** SKSE plugins register three callbacks on the `SKSESerializationInterface`: `SetSaveCallback`, `SetLoadCallback`, and `SetRevertCallback` (plus `SetFormDeleteCallback` and a `SetUniqueID`). Data is written as typed, versioned records via `OpenRecord(type, version)` / `WriteRecordData(...)`. The general co-save format is a header, then per-plugin headers, then per-plugin chunks of raw bytes. Higher-level libraries build on this: PapyrusUtil's StorageUtil ("save any amount of int, float, form and string values... accessed from any mod"), JContainers (JSON-serializable containers persisted in the save), and DKUtil's `serializable<T,"hash">`. PapyrusUtil's JsonUtil is notable because it writes to external `.json` files "stored independent of a user's save file" — data an external process can read directly, at the cost of losing atomicity with the `.ess`.

**Atomicity with the `.ess`.** The co-save shares the save's base name and lifecycle. SKSE's changelog notes "co-saves with the same name will now be deleted before written," and the message enum documents `kMessage_DeleteGame` as "sent right before deleting the .skse cosave and the .ess save." SSE Engine Fixes and standalone scripts routinely delete "orphaned" `.skse` files that have no matching `.ess`, confirming the intended 1:1 pairing. **Honest caveat:** the SKSE headers do not use the word "atomic" or promise transactional guarantees — `kPostLoadGame` carries a `bool` "true if game successfully loaded, false otherwise" precisely because a load can fail after `kPreLoadGame`, "which may require you to reset some of your plugin state." So the pairing is strong-by-convention, not crash-proof.

**Callback order and the Revert callback.** On load: `kPreLoadGame` (dispatched immediately before the save is read, with the `.ess` path) → each plugin's **Revert** callback (clears in-memory state to a clean baseline) → each plugin's **Load** callback (reads its records from the new co-save) → `kPostLoadGame` (after `LoadGame()` returns, with the success bool). Revert exists so stale data from the previously loaded session cannot leak into the newly loaded one; SKSE's own internal Revert clears all event registrations and object storage, and it also fires on new-game and quit-to-menu.

**Is a save-embedded UUID/timestamp the standard pattern for letting an external process identify the timeline?** It is a *sound* pattern and the right one — but it is not (yet) a widely-published Skyrim idiom. The clearest documented example of the concept is from another engine: the "realms" NWN module (GitLab Taro94/realms, issue #94) generates "a GUID... on module start" to "identify this module run uniquely," then writes periodic heartbeat timestamps and, on load, detects reloads by comparing recorded playtime stamps against the save's clock. In Skyrim, mods that need per-playthrough identity typically build it from PapyrusUtil/StorageUtil/JContainers plus a generated hash (e.g., auto-save mods that keep a per-character "playerhash" for save rotation), and reload detection is more often done with timestamps (CHIM's `gamets`) than with a stored GUID. The takeaway for your design: **embedding a UUID + monotonic generation counter in the co-save is strictly stronger than timestamp comparison** (it disambiguates same-clock forks and multiple same-named characters), and nothing in SKSE prevents it — you simply own both the writer (an SKSE/Papyrus shim) and the reader (your service).

### (3) How the event-sourcing community handles timeline forking and branch GC

Event sourcing stores state as an append-only, immutable log of events; current state is a fold over that log. Martin Fowler's canonical 2005 "Event Sourcing" essay names three facilities built on the log — **Complete Rebuild** ("the application's state can be thrown away and rebuilt only by looking at events"), **Temporal Query**, and **Event Replay** — and two of these map directly onto the Skyrim-reload problem:

- **Branching / forking.** Advanced event-sourced systems "support versioning and branching of event streams... to create alternative timelines or branches from a specific point in the event log," explicitly "analogous to branching in a version control system." The common implementation choices, as debated in the EventStore/KurrentDB community (issue #1693, "Branching with event store?"), are (a) a new stream per branch, or (b) capturing branch identity inside the events themselves. The Git analogy is exact: commit≈event, branch≈stream, `checkout`≈rehydrate-from-history, tag≈snapshot, "merge conflict"≈concurrency error. A player reloading an earlier save is a `git checkout` of an earlier commit followed by new commits — i.e., a fork.
- **Snapshots.** Because replaying a long log is expensive, systems periodically persist a materialized snapshot (a "save point for performance") and replay only events after it. This is exactly what CHIM's Playthrough Manager does when it backs up events/memories before pruning.
- **Branch garbage collection.** The hard part, as the community notes, is deletion-with-consistency: in the Atuin (shell-history sync) project's "Deleting history" discussion, maintainers observe "deletion with sync is difficult. Deleting on one machine would result in it coming back the next time a sync happens," and float tombstones and Merkle-tree-based reconciliation as the fix. The general answer to branch GC is: never hard-delete inline; mark branches abandoned with a tombstone/`abandoned_at`, keep them for a retention window (so an accidental reload is recoverable), and reap orphaned branches out-of-band once no live save references them — the same discipline SSE Engine Fixes applies when it deletes orphaned `.skse` co-saves with no matching `.ess`.

**Design implication:** model each Skyrim timeline as a branch (stream) identified by your `(save_uuid, generation)` key; snapshot at each save; never destructively roll back on reload — fork instead and tombstone the abandoned branch for later GC.

### (4) Runtime save-load detection and race conditions

**Detection hooks.** Papyrus exposes `OnPlayerLoadGame()` on the player Actor (or via `ReferenceAlias`/`ActiveMagicEffect`/remote registration). The critical caveat, stated in the CreationKit example scripts: **`OnPlayerLoadGame` will not fire the first time** (on a brand-new game) — the standard idiom is to call the same maintenance routine from both `OnInit()` (fires on new game) and `OnPlayerLoadGame()` (fires on every subsequent load). At the native layer, SKSE dispatches `kPreLoadGame`/`kPostLoadGame` messages, with `kPostLoadGame` carrying a success bool.

**Race conditions relevant to an external service:**
- **Two non-synchronized "load done" signals.** `kPostLoadGame` (C++/native, earlier) and `OnPlayerLoadGame` (Papyrus, later, and *absent on new game*) do not coincide. A service told "loaded" by the native message may be notified while the Papyrus VM is still spinning up and forms are unresolved; a service relying only on Papyrus gets no signal at all on a new game.
- **Papyrus-not-ready gap.** Papyrus logs routinely show post-load handlers erroring on not-yet-resolved objects (e.g., "Cannot call ... on a None object" / "File does not exist or is not currently loaded") immediately after load, evidence that referenced forms/dependent scripts may not be initialized at the instant load "completes."
- **Load can fail after PreLoad.** As above, `kPostLoadGame`'s bool exists because a save can error mid-load, so a service must not commit state changes on PreLoad optimism.
- **Throughput races.** SkyrimNet's own bug tracker ("SkyrimNet cannot keep up with game load") shows that a burst of state at load time can overwhelm the consumer — an external process must be back-pressure-tolerant.
- **Clean-reload confounders.** Because Skyrim's engine leaks references across in-session reloads (the basis of the "clean save" folklore and mods like Clean Save Auto-reloader, which forces a full restart on the second load), the *game* state after an in-session reload is itself less trustworthy — another reason to fork rather than trust in-place continuity.

## Recommendations

Adopt an **event-sourced, fork-on-reload protocol** anchored to a save-embedded identity. Stage it as follows.

**Stage 1 — Establish a durable timeline identity (do this first).**
- Ship a thin SKSE/Papyrus shim. On **new game** (`OnInit()` path, since `OnPlayerLoadGame` won't fire), generate `save_uuid = UUIDv4` and set `generation = 0`. Persist both in the co-save via PapyrusUtil/StorageUtil or a small SKSE record (so they travel atomically with the `.ess`).
- On **every save** (`kSaveGame`/`OnPlayerLoadGame` maintenance), also write a monotonic `event_seq` (your log head at save time) and the current `gamets` into the co-save. This triple `(save_uuid, generation, event_seq)` is your **watermark**.
- Mirror the watermark to a sidecar file your service can read directly (JsonUtil-style) as a fallback for when the co-save isn't parseable out-of-process.

**Stage 2 — Make the service an append-only event store.**
- Key every event by `(save_uuid, generation)` = a **branch**. Never UPDATE/DELETE events; append only. Maintain a per-branch head (`event_seq`, `gamets`).
- Snapshot NPC beliefs/rumors/relationships per branch at each save (cheap rehydration, mirroring CHIM's Playthrough-Manager snapshot discipline).

**Stage 3 — Reconcile on load (fork, don't roll back).**
- On load, have the shim push the loaded save's watermark to the service **before** any new event is allowed to commit (this closes the `kPostLoadGame`/Papyrus race — gate writes on receipt of the watermark, not on the load message).
- Compare loaded `event_seq`/`gamets` to the branch head:
  - **Equal (continue):** same timeline, keep appending.
  - **In the past (reload/death-reload):** **fork** — increment `generation`, copy forward the snapshot at the loaded watermark, and route new events to the new branch. Tombstone the now-abandoned suffix (mark `abandoned_at`), don't delete it.
  - **Unknown `save_uuid` (different character/slot):** switch to (or lazily create) that character's branch set — this is what fixes Mantella's same-name collision and CHIM's global-store multi-character problem.
- Because you carry a UUID, you never rely on `gamets` alone (which CHIM does and which cannot distinguish two forks that share a clock value).

**Stage 4 — Branch garbage collection.**
- Keep abandoned branches for a retention window (e.g., configurable N days / M forks) so accidental reloads are recoverable.
- Reap out-of-band: a branch is collectible when no existing `.ess`/co-save references its `(save_uuid, generation)` — the same "orphaned co-save" test SSE Engine Fixes uses. Use tombstones so a resurrected save can't silently un-delete via any future sync (the Atuin lesson).

**Stage 5 — Hardening.**
- Treat load as "ready" only after the Papyrus shim confirms forms are resolved (send an explicit `game_ready` ping distinct from `kPostLoadGame`); until then, buffer/queue.
- Make the service idempotent and back-pressure-tolerant (SkyrimNet's "can't keep up" failure): dedupe on `(save_uuid, generation, event_seq)`.
- Version your co-save records (SKSE `OpenRecord` version arg) so schema upgrades don't corrupt old branches.

**Benchmarks / thresholds that would change the plan.** If you can guarantee **single-character, single-slot, never-reload** play, skip forking and use a linear log (Stage 3 collapses to "continue"). If you can move **in-process** (a DLL like SkyrimNet) you can read the watermark from memory and drop the sidecar file and much of the race handling. If write volume is low (a few events/minute) a plain SQLite event table per branch suffices; only reach for a dedicated event-store/vector DB if you exceed roughly tens of events/second or need semantic recall like CHIM's ChromaDB. If you observe branch counts exploding from habitual quicksave/quickload, raise the fork threshold — only fork when the backward `gamets` jump exceeds a configured delta (echoing CHIM's "DragonBreak"-style trigger for loading old saves) so trivial same-point reloads don't spawn branches.

## Caveats
- **Vendor internals are partly inferred.** CHIM's exact fork/prune logic is reconstructed from its FAQ, Nexus changelog, and the HerikaServer timestamp fields. The user-facing docs describe deleting "future" events and backing them up to the Playthrough Manager under a "DragonBreak"; **the specific numeric trigger (a threshold in in-game days) could not be confirmed in any Dwemer Dynamics source and should be treated as uncorroborated.** Mantella's and SkyrimNet's "ignore" behavior is inferred from their documented file/in-process architecture and the absence of reload-reconciliation features, not from an explicit "we do nothing on reload" statement.
- **These projects move fast.** CHIM (v2.0), Mantella (v0.12+ HTTP, plus forks like Pantella/DreaminALife), and SkyrimNet are all actively developed; specific behaviors and file paths may change after this writing (August 2026).
- **SKSE atomicity is by convention.** The `.skse`/`.ess` pairing is enforced by naming and lifecycle, not a transactional guarantee; a crash between writes, or a failed load after `kPreLoadGame`, can desynchronize them — hence the Stage-5 idempotency/versioning guards.
- **`gamets` is not a globally unique timeline key.** It is seeded identically (10,000,000) on every new save and advances with in-game time, so two different playthroughs or two forks can share values — the reason this report recommends a UUID rather than CHIM's clock-only approach.
- **The UUID-in-cosave pattern is under-documented for Skyrim.** The strongest published precedent is from another engine (NWN "realms"); expect to implement and test the co-save read path yourself rather than rely on an off-the-shelf Skyrim library that already does exactly this.
