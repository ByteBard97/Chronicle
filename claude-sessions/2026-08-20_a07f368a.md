helper guards the confidence-like fields. Added a comment explaining why
`Evidence.strength` is deliberately the teller's pre-decay confidence,
not the hearer's post-decay belief (kimi flagged this as possibly
inconsistent; it's intentional -- the evidence should record the
testimony's strength as given). Added four more tests for the new
guards. 10 tests pass, ruff clean.

Implemented the next slice of propagation machinery: `decay()` (rule 6)
as a free, read-time-only function on `BeliefInstance` -- confidence/
verbatim/gist erode by elapsed time since `last_rehearsed` via
exponential half-life, verbatim decaying faster than gist (rule 5),
computed lazily per rule 19 rather than written back into the store --
and `ClaimStore.corroborate()` (rule 7): independent testimony from a
distinct source raises confidence via noisy-or combination, repetition
from the same source is rejected. An advisor pass caught three real bugs
before this was called done: (1) `corroborate()` combined raw stored
confidences instead of decaying both beliefs to the query time first, so
long-unrehearsed corroborating testimony would have counted at full
original strength; (2) it didn't reject self-corroboration (an NPC
"corroborating" their own belief) or a stale `source_belief` (a copy
captured before an earlier `corroborate()` call replaced that belief
id) -- both fixed, both tested. Extended
`scenarios/test_jarl_death_belief_cascade.py` to prove decay and
corroboration in cascade context, not just unit tests: Irileth
independently witnesses the same death and corroborates Proventus's
belief, and querying the story's strength after a ~week-long
rehearsal-free gap shows it eroded rather than staying frozen. Writing
that scenario surfaced a real gap live: `witness()` had no guard against
two independent witnesses to the same event creating two *different*
`Claim` records (I made exactly this mistake first-draft, giving Irileth
a separate `claim_id`). Fixed with a store-level check in
`ClaimStore.witness()` -- same `canonical_event_key` must resolve to the
same `claim_id`, and the same `claim_id` must carry identical content
(a second check an advisor pass caught was still missing after the
first fix: nothing stopped the same `claim_id` from being silently
overwritten with different slots, which would have retroactively
changed what every existing belief pointing at it resolves to). Added
this as **rule 21** in `docs/v0.1-spec.md` since it's a real constraint
the ADRs didn't previously state anywhere outside a `ValueError` string.
