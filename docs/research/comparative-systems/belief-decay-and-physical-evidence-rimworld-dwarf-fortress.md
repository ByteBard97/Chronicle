# Legible Social Simulation and Physical Evidence in Dwarf Fortress and RimWorld: A Technical Research Report for "Chronicle" (Skyrim SE/AE)

## TL;DR
- **Adopt a hybrid decay model:** use RimWorld's cheap, recompute-on-demand, time-limited stacking thoughts as the mechanical skeleton for Chronicle's belief graph, but graft on Dwarf Fortress's *capped emotional-memory buffer* (8 short-term + 8 long-term slots, grouped, strongest-wins) for the small set of "core" beliefs each NPC carries — and, critically, split belief into **two independent scalar axes** (strength/confidence and accuracy/distortion) that decay on separate curves, because neither DF nor RimWorld actually models the accuracy axis and that is the novel part of your design.
- **For physical evidence in first person, copy DF's "inspect-the-object-to-read-its-provenance" pattern but not its UI:** DF engravings, memorial slabs, and artifact descriptions are generated from serialized links to specific historical figures and events (`histfig_id`, `event_id`), and the game surfaces that provenance as readable prose ("This is an image of X and Y… X is raising Y…"). That maps almost perfectly onto Skyrim's first-person "activate an object → read a note/book/description" idiom. What does *not* transfer is DF's top-down "query any tile" omniscience and its list-based Legends browser.
- **Watch simulation scale:** DF long-world save folders reach hundreds of MB to 1–2 GB because the historical event log grows without bound; RimWorld avoids this by aggressively garbage-collecting expired thoughts. For a Python service driving Skyrim over SKSE/Papyrus, keep the authoritative graph in Python, expose only a thin per-cell/per-NPC slice to Papyrus (via SKSE co-save or JSON), cap event-log growth with decay-based pruning, and never traverse the whole graph on the Papyrus side.

---

## Key Findings

1. **Dwarf Fortress memory (post-v0.44) is a fixed-slot, grouped, strongest-wins buffer with intensity decay driven by personality, not a scalar mood.** Each dwarf has 8 short-term + 8 long-term memory slots plus an effectively unbounded "core" memory tier; thoughts are grouped so only the strongest emotion per group holds a slot; weakest memories cycle out; promotion to long-term requires surviving roughly a year; core memory causes permanent personality change.
2. **DF stores world history separately from personal memory.** Historical events are global `historical_event` objects in a world-wide log; a dwarf's *personal* memory is a small local buffer that merely references circumstances. This two-tier split (global canonical log vs. per-agent lossy cache) is the single most transferable architectural idea for Chronicle.
3. **RimWorld opinion is recomputed on demand, never stored.** `Pawn_RelationsTracker.OpinionOf(other)` sums thought-stage offsets + relationship base opinions + trait modifiers every time it is queried. Memory thoughts (`Thought_Memory`) carry a `durationDays` and `stackLimit`; by default they hold full strength then vanish at expiry, with optional linear decay via `lerpOpinionToZeroAfterDurationPct`.
4. **DF makes provenance physically inspectable.** Engravings, slabs, and strange-mood artifacts serialize links to specific historical figures/events and generate readable descriptions naming those figures and events; slabs additionally carry the figure link that lets them lay a specific ghost to rest.
5. **DF's rumor system tracks per-figure secondhand knowledge with time-stamped, distance-based fade, but does NOT distort content** (except identity of secret-identity figures). This is a crucial negative lesson: your per-hop *distortion* axis has no precedent in either game and must be designed from scratch.

## Details

### 1. Dwarf Fortress: memory decay (post-v0.44 personality/stress rewrite)

**Data structure — fixed slots, not a scalar and not a FIFO.** The v0.44.10 rewrite gave each dwarf three memory stores: **8 short-term slots, 8 long-term slots, and a large core-memory store** (DF Wiki, *DF2014:Memory (thought)*). An open-source reimplementation of the documented rules, the `flokey82/go_gens/simmemory` package, encodes concrete constants that match community understanding: "Short-, and long term memory have 8 slots… while core memory has 32 slots… we promote thoughts from short to long memory after 10 days, and from long to core memory after 255 days." DF creator Tarn ("Toady One") Adams summarized the same structure: "Once a year passes, a short-term memory can be saved to one of eight long-term memory slots (if it is stronger than the current memories), or else it is forgotten. Long-term memories periodically return to affect the dwarf forever, until they are overwritten." This is confirmed at the struct level by DFHack's `df-structures`: `unit_personality` contains an `emotions` vector (`vector<unit_personality.T_emotions*>`), plus `values`, `dreams`, `traits`, `stress_level`, `needs`, and focus fields (`current_focus`, `undistracted_focus`) — DFHack/df-structures issue #299 dumps a live `unit_personality` showing `emotions` as a length-2 vector and `stress_level = 40`. Personal memory is thus a small bounded vector of emotion records, not a scalar counter.

**How thoughts attach to emotions.** A circumstance (e.g., "caught in the rain," "saw a dead body") produces a **thought**, which evokes an **emotion** whose sign and intensity depend on the dwarf's personality facets and values. The DF Wiki *Emotion* page enumerates 170 defined emotions (130 implemented), each with a "Divider" that scales its effect on stress; positive emotions carry negative stress numbers, and "numbers closer to 1 or -1 have the strongest effect." Low-strength emotions (divider 4/8) cannot push a dwarf into the most extreme happiness/unhappiness buckets — an explicit clamp so weak memories never dominate.

**Grouping, stacking vs. replacement.** Memories are grouped into categories; **only the strongest emotion in each group keeps a slot** (DF Wiki, *Memory*). When a new thought arrives: if its group already occupies a short-term slot, the stronger of {new, existing} is kept and the other discarded (replacement, not stacking); if the group is absent, it fills an empty slot or **overwrites the weakest existing memory of any group — even if that victim was stronger than the newcomer.** This produces "constant cycling of the weakest of the 8 memory slots," so at most 7 short-term memories have lasting effect. The `simmemory` reimplementation encodes exactly this rule ("overwrite the weakest memory … even if the overwritten memory is stronger than the new one").

**Promotion and the memory cap.** After a memory survives in short-term (the wiki describes this as roughly a year; `simmemory` uses 10 days as its tunable analogue), it attempts promotion to long-term: fills an empty long-term slot, else overwrites a weaker same-group memory, else overwrites the weakest long-term memory. Long-term slots are "retained forever … until overwritten by even stronger memories." Long-term memories are periodically *revisited* ("She felt satisfied remembering work"), each revisit re-applying a stress delta — the DF Wiki reports that "across a sample size of 300 dwarves… the median number of revisited memories was 9, with 83% of dwarves revisiting 8 or more long-term memories." On revisit a long-term memory has a 1-in-3 chance of promotion to **core memory**, which causes a permanent personality-facet/value change and is then removed from long-term (leaving a free slot). Core memories are rarely revisited but permanent.

**Intensity decay over time.** In the older (pre-rewrite) thought model, decay was an explicit halving: "after a month and a half … the modifier is halved and rounded away from zero" (DF Wiki, *23a:Thought*). In the current model, decay is expressed through the slot-cycling + personality-scaled emotion strength rather than a single documented half-life; emotion strength "depends on time elapsed and dwarven personality."

**Stress/focus counters and "unaffected by" thresholds.** Three personality traits govern stress dynamics (DF Wiki, *Stress*): `BRAVERY` (accumulation rate), `STRESS_VULNERABILITY` (breaking point), and `ANXIETY_PROPENSITY` (dissipation rate). Separately, **needs** drive a **focus** score (DF Wiki, *Need*): the focus ratio is a weighted average across need-satisfaction levels (Unfettered 6 → Badly distracted 2, divided by 4× the number of needs), and focus grants up to ±50% effective-skill modifier. This is a clean example of two *separate* decaying subsystems (stress vs. focus) driven off the same event stream — directly relevant to your "strength vs. accuracy" two-axis design.

**Historical events vs. personal memory (the two-tier split).** The world keeps a global log of `historical_event` objects generated during worldgen and ongoing play; only a small fraction of creatures are **historical figures** (`hist_figure_id != -1`) whose full histories are tracked, while the rest are abstracted/"offloaded" for memory reasons (DF Wiki, *Historical figure*). A dwarf's link to an event is recorded via the histfig/event references, and this is what feeds engravings, slabs, and legends. The lesson: **a canonical global event log + sparse per-agent references + a tiny lossy per-agent emotional cache.**

### 2. DF memorial slabs, engravings, and provenance

**What an engraving records.** Inspecting art normally shows only *what* it depicts, but with adventurer mode or the init option enabled, "inspecting a piece of art gives a history of what it depicts, including the names of those depicted" (DF Wiki, *Art*). Engravings reference specific historical figures and events; a worked community example: *"Engraved in this wall is an image of Ducim Speargraves the Dwarf and The Copper Gladness the yellow jasper bracelet. Ducim Speargraves is raising The Copper Gladness."* Community save-scumming research documents an internal *weighting* over which life-events get depicted (becoming a noble > writing a book > naming a weapon > killing a notable enemy > crafting an artifact > masterwork > profession change > marriage > migration), and that very recent events are disfavored — i.e., the provenance generator has priorities, not uniform random selection.

**Memorial slabs and ghosts.** A slab is engraved for a specific dead figure and, unlike a coffin, needs no body — so it can lay to rest a dwarf whose corpse is unrecoverable (DF Wiki, *Slab*). An engraved slab "contains information on the arrival and death of the creature" and, if the subject slew notable figures, names them; "if you're not sure how a dwarf or creature died, engraving a slab in their memory may reveal the killer." Reading is via `t`→Enter→`v` in fortress mode. Ghosts are laid to rest by burying the body **or** by engraving+building a slab for that figure; the link between slab and figure is explicit enough that the game announces "*[Name], Ghostly [profession] has been put to rest.*" Deconstructing the slab can re-raise the ghost (as a murderous ghost) — the provenance link is bidirectional and persistent.

### 3. RimWorld opinion dynamics

**Opinion is computed on demand, never stored.** The call chain (visible in a modded stack trace) is `Pawn_RelationsTracker.OpinionOf(Pawn)` → `ThoughtHandler.TotalOpinionOffset(Pawn)` → `GetSocialThoughts`. Opinion is a *sum*, recomputed each query, of: (a) social **memory thoughts** (insults, kind words, fights, "harmed me," etc.), (b) **relationship base opinions**, and (c) **trait/beauty modifiers**. Recomputing rather than storing is exactly the right model for a graph service that must reflect new evidence immediately.

**Thought_Memory: durationDays, stackLimit, decay curve.** From RimWorld's decompiled source (`MemoryThoughtHandler.cs`, `DebugOutputsMisc.cs`) and the RimWorld Wiki: each `Thought_Memory` has an `age` (ticks; 60,000 ticks/day) advanced by `ThoughtInterval()`, and is discarded when `age >= durationDays * 60000` (`RemoveExpiredMemories` / `ShouldDiscard`). **By default the moodlet holds full `baseMoodEffect`/`baseOpinionOffset` for its whole duration then vanishes instantly.** This is confirmed by the popular "All Memories Fade" mod (Mlie, Steam Workshop, first published Apr 26 2022), which "will force all memories fade out instead of just ending. For example instead of a divorce having -20 mood debuff for half a year and then vanish it will tick down over time"; the author confirms the taper "is a vanilla feature… This just exposes an existing mechanic to be configurable." Gradual decay is available via the ThoughtDef field **`lerpOpinionToZeroAfterDurationPct`**: past that fraction of the duration, the offset linearly lerps to zero, reaching zero at full duration. Duplicate thoughts don't stack unboundedly: `TryGainMemoryFast` calls `Renew()` (resetting `age` to 0) on the existing memory, and `stackLimit` / `stackLimitForSameOtherPawn` cap the count (trimming the **oldest**), while `stackedEffectMultiplier` gives diminishing returns per stacked copy (e.g., insults stack to 10× at ×0.9 each; social-fight thoughts stack to 5×).

**Concrete numbers (RimWorld Wiki, *Social*).** Social-interaction thoughts (Insulted −15, Kind words +15, Slighted −5, Deep talk +15) last 20 days, stack 10×, multiplier ×0.9. Actions: "Harmed me" −15/10 days; "Botched my surgery" −20/90 days; "Rescued me" +15/30 days; "Recruited me" +20/120 days. Family/romance relations contribute *base* opinions (spouse +30, lover +35, ex −15) plus death penalties (killed my spouse −65, killed parent/child/sibling −80). Traits apply flat permanent modifiers (Annoying voice −25, Abrasive multiplies insult chance ×2.3, Psychopath nullifies certain penalties, Kind ignores beauty/disfigurement and never insults). **Social fights:** every insult has a 4% chance to start one (slights 0.5%), and afterward the fight is randomly deemed cathartic (+38 opinion) or angering (−22), each 20 days.

**Design philosophy (Tynan Sylvester).** RimWorld was explicitly built around the pillar "Not a game – a story generator" (Sylvester's GDC 2017 talk, *RimWorld: Contrarian, Ridiculous, and Impossible Game Design Methods*), which he describes as the design pillar that "helped break assumptions." The readable-simulation payoff is that each pawn's mood/social tab lists *named, human-readable* thoughts with sources — the legibility comes from every number being attached to a plain-language cause. That is the standard Chronicle should hold every claim to: each belief must carry a legible provenance string.

### 4. DF artifact provenance (strange moods)

**What history feeds the artifact.** "An artifact is the ultimate expression of a dwarf's desires, fears, memories and hopes in art form" (DF Wiki, *Legendary artifact*). Decorations "are sometimes simple rings or spikes, or shapes or images (often drawn from preferences of the creator), or events in the history of the fortress or world history." So the description generator pulls from the creator's **preferences** and from **historical events/figures** the creator is linked to. The canonical example, *Planepacked*, is a statue whose engravings depict most of the world's history plus 73 images of itself.

**Serialization and inspectability.** Artifacts are added to the world's records; "these artifacts will be added to the world's records and its exact description can be viewed." The description is generated as prose ("This is a masterfully-designed engraving of a Dwarf and a battle axe…"; "On the item is an image of a dwarf in deer leather. The dwarf is dead."). A documented save bug — engravings/artifacts losing their subjects because "the game just forgot some of the history," leaving descriptions blank — confirms that the description text is generated at runtime from *links* to histfig/event records, not stored as a frozen string; when the referenced history is missing, the prose renders empty.

**Legends and world propagation.** Artifact creation history and storage locations "are recorded during world generation and can be discovered in Legends mode." From v0.47 (the "villains"/artifact-heist release, per the DF Wiki release notes), artifacts propagate: they can be stolen, moved, warred over, and become "symbols of various rulers." Toady noted (DF Talk #7) that a "destroyed" artifact isn't deleted but flagged Hidden and respawns elsewhere — artifacts are effectively immortal provenance anchors.

**The RUMOR system.** A rumor is "a certain piece of information regarding a specific historical event," originating from witnesses and re-spread by hearers (DF Wiki, *Rumor*). Knowledge of an artifact's location has **six discrete confidence levels** — from "having it yourself" → "saw it with your own eyes" → "heard so-and-so had it at a location recently" → "heard somebody has it (but not where)" → "generally known in legends-y fashion" → "no idea." Crucially: "The knowledge fades over the course of weeks and years while maintaining longer-term reputation effects … according to their time stamps (at the individual, site gov, site culture and civ levels)." So DF tracks secondhand knowledge **per historical figure**, at **four nested scopes**, with **time-stamped decay** — but **content is not distorted**: "no false rumors will ever spread," except misinformation about the *identity* of secret-identity figures (vampires, agents). Agents even store friendship **asymmetrically** (the agent sees an information source; the source sees a friend). Rumors spread when a knowing figure is "offloaded"; to prevent spread you must kill witnesses and hide corpses.

### 5. Comparisons to other legible-social-state games

- **Crusader Kings 2/3 — decaying opinion modifiers with timers.** CK3's `add_opinion` effect attaches a named, temporary modifier with an explicit timeout (`add_opinion = { modifier = X days/months/years = Y target = Z }`); if no timeout is given, the modifier's scripted default is used. CK2's modifiers historically snapped to zero at expiry; the community-desired and later-adopted improvement was **linear decay** (e.g., a +30 gift bonus losing ~6/year rather than vanishing). This is the cleanest external precedent for Chronicle's per-modifier decay timers, and it validates *named, sourced, individually-decaying* modifiers as a scalable pattern (Paradox forums; CK3 Wiki, *Modifiers*).
- **Shadow of Mordor — Nemesis system (physical memory made visible).** Orcs remember specific encounters and **surface that memory physically and in dialogue**. Per Monolith's statement to Kotaku (Oct 2014): "an orc who was slain by a headshot from an arrow may return with a metal eyepatch indicating he's lost an eye; or an orc who was burned in a fire may return with burn scar-tissue on his face; or an orc stabbed in the head may be covered in bandages." They also boast in showdown dialogue about how they last beat you. The transferable pattern: **encode an NPC's history as a small set of visible, player-readable tokens** (a scar, a callback line) rather than an opaque stat — exactly Chronicle's "guard armband / poison vial / bounty notice as legible evidence" goal.
- **RimWorld/DF** remain the primary models; Caves of Qud, Ultima Ratio Regum, and Wildermyth were reviewed but yielded no additional concrete, transferable implementation patterns beyond what DF/RW already provide, so they are not recommended as design references here.

### Implementation cautions (Python service + SKSE/Papyrus)

- **Save-game / log bloat.** DF save folders range "from just a few megabytes … to several hundred megabytes for large worlds with many events, and even a gigabyte or two … in extreme cases" (DF Wiki, *Saved game folder*), and long histories cause exponential worldgen/save/load time and crashes — because the historical event log grows unbounded. **Mitigation for Chronicle:** treat the global event log as append-only but *periodically compact* it — collapse fully-decayed claims, summarize old events into aggregate "reputation" scalars (as DF's rumor system keeps "longer-term reputation effects" after detailed knowledge fades), and cap per-NPC memory as DF caps slots.
- **RimWorld garbage collection.** RimWorld keeps memory cheap precisely because `RemoveExpiredMemories` prunes every thought at `age >= duration`, and opinion is recomputed rather than stored. **Chronicle should do the same:** never persist derived opinion; persist only claims (with strength, accuracy, provenance, timestamp) and prune on decay threshold.
- **Papyrus is the bottleneck, not Python.** Papyrus is a slow, latency-bound scripting VM; Skyrim is memory-constrained (the classic 32-bit build capped process memory near ~3.1 GB; SE is 64-bit but Papyrus throughput remains the constraint). Do **all** graph traversal in the Python core and hand Papyrus only a tiny, already-resolved slice (the claims relevant to the NPCs currently loaded / the object being inspected). Use an SKSE plugin or a PapyrusUtil/JContainers-style JSON co-save for the handoff (JContainers explicitly provides "arrays and associative containers… garbage collector" for exactly this, and JsonUtil "saves data to custom external .json files… stored independently of a user save file"); never store the full belief graph in Papyrus arrays or traverse it per-frame.
- **Feasible scale.** DF explicitly tracks only a sparse set of historical figures and abstracts the rest for memory reasons; RimWorld runs dozens of pawns with ~10–300-stack thought lists each. A realistic Chronicle target is **hundreds of tracked NPCs with tens of claims each and a bounded global event log**, with rumor propagation run on a coarse tick (e.g., per in-game hour or on cell-load) rather than continuously.

## Recommendation A — Memory decay model for a graph-based belief system

**Verdict: a hybrid, with RimWorld's recompute-on-demand thought mechanics as the skeleton and DF's capped emotional-memory buffer for a small "core beliefs" tier — plus a two-axis (strength × accuracy) model that neither game implements.**

**1. Represent a belief as a claim node, not a scalar.** Each claim: `{claim_id, subject, predicate, object, strength ∈ [0,1], accuracy ∈ [0,1], provenance_chain, first_heard_tick, last_reinforced_tick, source_figure_id}`. Opinion/attitude toward a person is *derived on demand* by summing relevant claims + relationship base + trait modifiers (RimWorld's `OpinionOf` pattern) — never stored.

**2. Two independent axes with different decay curves.** This is the crux and is *not* borrowed from DF or RW (DF rumors never distort; RW has no accuracy axis):
- **Strength (confidence):** decays like a RimWorld memory. Default: hold full strength for a "fresh" window, then **linear lerp toward a floor** (RimWorld's `lerpOpinionToZeroAfterDurationPct` pattern) — or, better, an **exponential half-life** `strength *= 0.5^(Δt / half_life)`, which is smoother and matches CK-style and DF-rumor "fades over weeks and years." Reinforcement (hearing the same claim again) resets `last_reinforced_tick` (RimWorld's `Renew()`), and repeated corroboration can *raise* strength toward 1.0.
- **Accuracy (distortion):** **monotonically degrades with provenance-chain length and never self-heals** except by contact with ground truth (witnessing the physical evidence, or hearing from a first-hand witness). Model accuracy as multiplicative per hop: `accuracy_child = accuracy_parent × (1 − noise_per_hop)`, with `noise_per_hop` modulated by the transmitting NPC's traits (a gossipy or dim NPC injects more noise). Keep the two axes separate because a rumor can be *strongly believed but wildly inaccurate* (the interesting failure mode your design wants).

**3. Per-hop degradation — concrete mechanics.**
- **Multiplicative strength decay per hop:** `strength_child = strength_parent × hop_retention` (e.g., 0.8), so a claim 5 hops from the witness starts at ~0.33 strength. This mirrors DF's six discrete artifact-knowledge tiers, but as a continuous scalar.
- **Content noise injection into the claim, gated by accuracy:** when accuracy drops below thresholds, mutate the claim's fields probabilistically — swap `object` to a plausible neighbor ("killed the Jarl" → "killed a guard"), soften the predicate, or replace the `subject`/`object` identity (exactly DF's *only* sanctioned distortion: identity of secret-identity figures). Store the mutation history so the player can, in principle, trace the corruption.
- **Provenance-chain length effects:** cap effective chain length (DF caps memory slots; you cap hops) — beyond N hops a claim collapses to a low-strength, low-accuracy "legends-y" tier (DF's fifth knowledge level: "generally known in some legends-y fashion").

**4. Capped per-NPC buffers (from DF).** Give each NPC a bounded working set: e.g., 8–16 "active" claim slots that drive behavior, grouped by subject so only the strongest claim per subject stays hot (DF's grouped strongest-wins rule), plus an unbounded-but-compacted "core beliefs" set for identity-defining claims (DF core memory → permanent personality change; note DF's own tiers of 8/8/32 slots as a starting calibration). This bounds per-NPC cost and gives you DF's emergent "constant cycling of the weakest slot."

**5. Tick rates.** Don't decay every claim every frame. Use RimWorld's interval pattern: run a decay/pruning pass on a coarse tick (per in-game hour or on NPC load), lazily applying `strength *= 0.5^(Δt/half_life)` using stored timestamps (so cost is O(claims touched), not O(all claims × ticks)). Prune claims whose strength falls below a floor (RimWorld's `RemoveExpiredMemories`).

**6. Ground-truth anchors.** Physical evidence (below) resets accuracy to 1.0 and strength high for any NPC who inspects it — the counterweight to distortion, and the mechanic that makes investigation meaningful.

## Recommendation B — Physical-evidence pattern for a first-person RPG

**Verdict: adopt DF's "object carries serialized links to specific figures/events, rendered as readable prose on inspection" pattern; discard DF's omniscient top-down query UI and Legends list-browser.**

**What DF gets right and transfers:**
- **Evidence objects are generated from provenance links, not hand-authored strings.** A slab links to a `histfig_id`; an engraving links to an `event_id` + figures; the description prose is generated at runtime from those links (proven by the save bug that blanks descriptions when the referenced history is lost). **Chronicle should do the same:** a memorial shrine, bounty notice, guard armband, or poison vial is a thin object holding `{event_id, figure_ids, generated_at_tick}`; when the player activates it, the Python service resolves the links and returns generated prose ("This bounty notice names the Dragonborn for the murder of Jarl Balgruuf, sworn by a guard of Whiterun, 4 days ago").
- **Provenance is legible and specific.** DF names the figures and the relationship ("X is raising Y"; "the killer is listed at the end"). Chronicle's evidence should always name *who*, *what*, *when*, and *from whom* — the same fields as a belief node — so an object is literally a materialized, high-accuracy claim.
- **Evidence as ground-truth anchor.** DF slabs definitively resolve "how did they die / who killed them"; inspecting one is authoritative. In Chronicle, inspecting evidence should set accuracy=1.0 for the inspecting NPC/player — the antidote to rumor drift.
- **Evidence persists and can move/be destroyed-but-not-deleted.** DF artifacts get a Hidden flag and respawn rather than vanish; slabs can be deconstructed to re-raise a ghost. Chronicle evidence should be durable and its removal should itself be an event (removing a bounty notice is a social act).

**What does NOT transfer:**
- **DF's top-down "query any tile / read any dwarf's full thought list" omniscience.** In first person the player cannot inspect everything at once; information must be *discovered* by physically approaching and activating objects and by talking to NPCs. This is a feature, not a limitation — it makes the social state a mystery to investigate.
- **The Legends list-browser.** A spreadsheet of all events breaks first-person immersion. Replace it with **diegetic surfaces**: books/notes/letters the player reads, NPC dialogue that quotes their current top claims, and evidence objects. RimWorld's lesson reinforces this: legibility comes from every value being attached to a plain-language, in-world cause.

**First-person-specific patterns to add:**
- **Tiered reveal on inspection** mirroring DF's six knowledge levels: a distant/rumored NPC gives vague dialogue ("they say the Dragonborn did something terrible"); an eyewitness or a physical document gives specifics. Let the player's *own* investigation raise their knowledge tier.
- **Nemesis-style visible tokens:** make an NPC's key beliefs/experiences physically visible where possible (a guard who believes you're a murderer wears an armband, adopts hostile idle dialogue that references the specific event) so social state is readable at a glance, not only via menus — exactly the Shadow of Mordor scar/eyepatch/callback pattern.
- **Dialogue as the primary read interface:** since Skyrim players talk to NPCs, expose each NPC's top-N strongest claims as dialogue topics, tagged with confidence ("I heard…", "I'm certain…", "I saw it myself") that directly reflects the strength/accuracy axes.

## Recommendations (staged, with thresholds)

**Stage 1 — Core belief graph (Python only).** Implement claim nodes with the two-axis model, recompute-on-demand attitudes (RimWorld pattern), exponential-half-life strength decay, and per-NPC capped buffers (DF pattern). *Benchmark to proceed:* decay+prune pass over a full graph of ~200 NPCs × ~30 claims completes in <10 ms on a coarse tick.

**Stage 2 — Rumor propagation.** Add per-hop multiplicative strength decay + accuracy degradation + gated content mutation, run on NPC-load/coarse tick. *Benchmark:* propagation from one witness stabilizes across a village within a plausible in-world window (hours–days) without runaway claim proliferation; cap hops at N (start N=5, tune).

**Stage 3 — Physical evidence.** Materialize high-impact events as inspectable objects carrying provenance links; inspection returns generated prose and sets accuracy=1.0 for the inspector. *Benchmark:* an evidence object's description regenerates correctly after a save/reload cycle (the DF failure mode to avoid — never freeze prose, always regenerate from links, but guarantee the referenced event/figure records are preserved in the co-save).

**Stage 4 — Papyrus integration & scale hardening.** Expose only the loaded-cell slice to Papyrus via SKSE/JSON; move all traversal to Python; add event-log compaction (collapse fully-decayed claims into aggregate reputation scalars). *Thresholds that change the plan:* if co-save size grows beyond a few MB or handoff latency is perceptible, reduce tracked-NPC count, shorten half-lives to prune faster, or lower per-NPC slot caps. If distortion makes the world feel incoherent, reduce `noise_per_hop` or widen the fresh-window before strength decay begins.

## Caveats
- **The accuracy/distortion axis has no direct precedent.** DF's rumor system explicitly never spreads false content (only secret-identity confusion), and RimWorld has no accuracy concept at all. Chronicle's per-hop *content distortion* is genuinely novel and must be prototyped and tuned empirically; the games only validate the *strength* axis and the *provenance-chain/decay* scaffolding.
- **Some DF internals are community-reverse-engineered, not official.** The 8+8 slot counts, grouping, and promotion rules come from the DF Wiki, player experimentation (including a 300-dwarf sample), and the `simmemory` reimplementation, corroborated by Tarn Adams' own description of the year-based short→long promotion; Toady confirmed the existence of a core-memory exclusion list but "couldn't recall what was on it." Treat exact numbers (e.g., 32 core slots, 10-day/255-day promotion thresholds) as well-supported approximations from the reimplementation, not verbatim engine spec.
- **RimWorld decay specifics are from decompiled source.** The `lerpOpinionToZeroAfterDurationPct` field, `Renew()` age-reset, and `ShouldDiscard` removal are confirmed from decompiled `MemoryThoughtHandler.cs`/`DebugOutputsMisc.cs` and corroborated by the "All Memories Fade" mod author; the exact default of `lerpOpinionToZeroAfterDurationPct` and any vanilla def setting it to a specific value (e.g., 0.7) were not verbatim-confirmed — vanilla default behavior is abrupt expiry.
