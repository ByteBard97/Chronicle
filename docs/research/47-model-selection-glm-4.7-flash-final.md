## TL;DR — the decision

**Primary pick: GLM-4.7-Flash** (zai-org, 30B total / ~3B active MoE, MIT). It is the only current-generation 30B-class model that is **pure full attention** — Multi-Head Latent Attention (MLA), no sliding-window layers, no recurrent/SSM/DeltaNet layers — so the prefix-cache landmine does not apply on either llama.cpp or MLX. It out-benchmarks Qwen3-30B-A3B-Thinking-2507 on every published row, has explicit positive roleplay/creative-writing feedback, has merged official llama.cpp support plus `glm4_moe_lite` support in mlx-lm main, and decodes at roughly 24–26 tok/s on M4/M5-Max-class silicon (M5 Pro projection ≈ low-20s), comfortably above the 15 tok/s bar.

**Fallback: Qwen3-30B-A3B-Instruct-2507** (Apache 2.0). Same MoE shape as the original pick (30B total, 3.3B active), pure GQA full attention, the most battle-tested model family on both Apple Silicon serving stacks, non-thinking by design (zero reasoning-trace cache churn), Creative Writing v3 score of 86.0, and ~35 tok/s decode on a *24GB M4 Pro* — i.e., ~38–40 tok/s projected on the M5 Pro. If GLM-4.7-Flash shows any behavioral problem in Chronicle's harness, this swap is a one-line model-path change with no architectural risk.

**Gemma-4-26B-A4B is not the answer.** It fails requirement 1 outright: the Gemma 4 technical report confirms a 5:1 interleaved local sliding-window / global attention pattern ([Gemma 4 Technical Report](https://arxiv.org/html/2607.02770v1)). Worse, it fails on llama.cpp for a *second, independent* reason: its shared-KV layers make llama-server log "cache reuse is not supported" even with `--swa-full` ([llama.cpp issue #21468](https://github.com/ggml-org/llama.cpp/issues/21468)). It is eliminated twice over, on both serving stacks.

## 1. The blocker, verified

The premise of Prompt 44 checks out against primary sources. Qwen3.6-35B-A3B's own Hugging Face card specifies a 40-layer layout of `10 × (3 × (Gated DeltaNet → MoE) → 1 × (Gated Attention → MoE))` — three of every four layers carry a fixed-size recurrent state rather than a per-token KV cache ([Qwen/Qwen3.6-35B-A3B](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)). On llama.cpp this produces exactly the quoted failure: `forcing full prompt re-processing due to lack of cache data (likely due to SWA or hybrid/recurrent memory)` on every turn, confirmed across the Qwen3.5/3.6 family in the issue tracker and in independent field reports ([llama.cpp issue #20225 via ai-muninn](https://ai-muninn.com/en/blog/why-30-toks-feels-slower-than-14-ttft), [particula.tech teardown](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)). One measured case: a 15K-token conversation took ~8 minutes per turn instead of seconds ([ai-muninn](https://ai-muninn.com/en/blog/why-30-toks-feels-slower-than-14-ttft)). The sibling dense model Qwen3.6-27B is hybrid too (48 DeltaNet + 16 attention layers), so there is no in-family escape ([vLLM forums](https://discuss.vllm.ai/t/support-for-qwen3-6-27b-35b-a3b-hybrid-gated-deltanet-models-on-tpu-v5e-8-with-vllm-and-sglang/2875)).

On MLX the situation is the same by root cause: mlx-lm issue #980 establishes that prompt prefix caching "only works for pure full-attention models," with sliding-window, Mamba/SSM, and mixed-attention models all silently falling back to full recomputation; the recurrent state cannot be trimmed at an arbitrary token boundary ([mlx-lm #980](https://github.com/ml-explore/mlx-lm/issues/980)). The upstream fixes are not landing soon: the llama.cpp route is RAM-resident partial-state checkpoints whose flags churned repeatedly through mid-2026 (`--checkpoint-every-n-tokens` deleted by PR #22929, replaced by `-cms`/`-ctxcp` with changed semantics), with disk-backed checkpoints still an unanswered feature request ([particula.tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)); on MLX the relevant PRs (#923, mlx-engine #188/#192) remain unmerged ([mlx-lm #980](https://github.com/ml-explore/mlx-lm/issues/980)). The only engines with real hybrid prefix caching are vLLM and SGLang — both CUDA-oriented and a poor fit for a memory-bound 64GB unified-memory box. The particula teardown's own mitigation table says it plainly: **"Switch to a full-attention model … Removes the problem entirely"** ([particula.tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)). Model selection is the correct fix; this is not a tuning problem.

One correction to the brief's framing, worth noting because it affects the fix's shape: llama.cpp's "need explicit per-location warm cache files" claim (from the original Prompt-40-era assumption) understates current llama-server. Prompt caching (`--cache-prompt`) is **on by default**, slot assignment uses longest-prefix similarity (`-sps`, default 0.10), partial-prefix reuse within a slot is automatic, reuse is observable per-request as `timings.cache_n`, and `--cache-reuse N` adds KV-shifting for near-miss prefixes ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [llama.cpp tutorial #13606](https://github.com/ggml-org/llama.cpp/discussions/13606)). Manual `/slots/{id}?action=save|restore` to disk exists for cross-restart warmth, but the day-to-day shared-prefix reuse Chronicle needs is automatic — **for full-attention models only**. The entire failure is architecture-gated, which is exactly why swapping the model is sufficient.

## 2. Requirement 1 screening: what is actually full attention in September 2026

The screening rule was mechanical: read each candidate's real architecture (model card, config.json, technical report), and reject anything with sliding-window, recurrent/SSM/Mamba/DeltaNet, chunked, or sparse-indexed attention layers. The hybrid wave hit almost the entire 2025–2026 release window, so this filter eliminates most fashionable models — including some that look like they should be safe.

The structural observation: **2026's 30B-class releases are almost all hybrid** because vendors optimized for long-context cost, and prefix caching on llama.cpp/MLX is the casualty. The viable full-attention set in the 20–40B class reduces to three names: GLM-4.7-Flash, the 2025 Qwen3 family (30B-A3B and 32B), and Mistral Small 3.x 24B. Of these, only GLM-4.7-Flash is a current-generation capability match for the model being replaced; the Qwen3 entry is one generation back but maximally proven; Mistral Small 3.2 is a tier below both for dialogue quality. Note also what "full attention" must mean here: MLA (GLM-4.7-Flash, DeepSeek family) qualifies — every token still attends to every previous token, and the compressed latent KV is stored per-token and is truncatable exactly like GQA KV. The disqualifying property is not cache *size* or compression; it is state that cannot be split at an arbitrary token boundary (recurrent state) or a cache that wraps (sliding window) ([particula.tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache), [mlx-lm #980](https://github.com/ml-explore/mlx-lm/issues/980)).

## 3. Primary pick: GLM-4.7-Flash

### 3.1 Why it satisfies every requirement

**Architecture (req 1).** GLM-4.7-Flash's config declares `Glm4MoeLiteForCausalLM` — an MoE with Multi-Head Latent Attention, 47 layers, 64 routed experts plus 1 shared, ~3B active per token, and the MLA parameter block (`kv_lora_rank 512`, `q_lora_rank 768`, `qk_rope_head_dim 64`) with **no sliding-window setting and no recurrent layers anywhere in the configuration** ([solarkyle/GLM-4.7-Flash-GGUF](https://huggingface.co/solarkyle/GLM-4.7-Flash-GGUF), [mlx-lm glm4_moe_lite.py](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/glm4_moe_lite.py)). In llama.cpp it is converted through the DeepseekV2 model class — the same MLA cache lineage as DeepSeek-V2/V3, for which no prefix-cache breakage has ever been reported, because latent KV truncates cleanly per token ([solarkyle conversion notes](https://huggingface.co/solarkyle/GLM-4.7-Flash-GGUF)). This is the single most important property in this report, and it is confirmed from the architecture description rather than assumed from the name, as required.

**Capability (req 2).** Z.ai's published table has GLM-4.7-Flash beating Qwen3-30B-A3B-Thinking-2507 and GPT-OSS-20B on every listed benchmark — AIME 25: 91.6 vs 85.0; GPQA: 75.2 vs 73.4; SWE-bench Verified: 59.2 vs 22.0; τ²-Bench: 79.5 vs 49.0; BrowseComp: 42.8 vs 2.29 ([zai-org/GLM-4.7-Flash](https://huggingface.co/zai-org/GLM-4.7-Flash)). For Chronicle's actual workload — grounded NPC dialogue rendering — the more relevant evidence is community reception: early adopters describe it as "good in roleplay and creative writing. Really good logic too," with the caveat that at reasoning-budget 0 it can occasionally sneak a thought fragment into output ([HF discussion #44](https://huggingface.co/zai-org/GLM-4.7-Flash/discussions/44)). It is the strongest open 30B-class model currently shipping ([xigh open-weight-models](https://github.com/xigh/open-weight-models)) and, unlike the Qwen3.6 it replaces, it carries no vision encoder or other baggage Chronicle doesn't need — it is a text model with a 200K-class context (max_position 202,752) ([unsloth guide](https://unsloth.ai/docs/models/tutorials/glm-4.7-flash)).

**Serving support and throughput (req 3).** Official llama.cpp support merged in January 2026 with maintained unsloth GGUF quants, and the model runs on the Metal backend on 64GB unified-memory Macs — the known early wrinkles (a `scoring_func` softmax-vs-sigmoid bug causing loops, and a chat-template tool-call regression in builds 7761–7802) were both fixed within days and are non-issues on any current build ([unsloth guide](https://unsloth.ai/docs/models/tutorials/glm-4.7-flash), [unsloth GGUF discussion](https://huggingface.co/unsloth/GLM-4.7-Flash-GGUF/discussions/10)). On the MLX side, `mlx_lm/models/glm4_moe_lite.py` now exists on mlx-lm main — the January 2026 "not supported" issue #806 is resolved in-tree ([mlx-lm #806](https://github.com/ml-explore/mlx-lm/issues/806), [mlx-lm source](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/models/glm4_moe_lite.py)). Published Apple Silicon estimates put Q4_K_M decode at ~26 tok/s on an M5 Max 64GB and ~24 tok/s on an M4 Max 48GB ([llmcheck.net benchmarks](https://llmcheck.net/benchmarks)); interpolating by memory bandwidth to the M5 Pro's 307GB/s lands in the low-20s — above the 15 tok/s requirement with margin. Weights are only ~17–19GB at Q4, and MLA's compressed KV keeps long-context cache small, leaving ample headroom in the 64GB budget for the resident TTS model ([unsloth guide](https://unsloth.ai/docs/models/tutorials/glm-4.7-flash)).

**Prefix-cache behavior (req 4).** The honest evidentiary position: no one has yet published a `cache_n` trace specifically for GLM-4.7-Flash on llama-server. What exists is one level up and is strong: (a) llama-server's prefix-reuse machinery — `--cache-prompt` on by default, similarity-based slot assignment, per-request `timings.cache_n` reporting, documented partial-prefix reuse logs, and `/slots` save/restore — is architecture-independent code that only bails out for SWA/hybrid-recurrent contexts ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [tutorial #13606](https://github.com/ggml-org/llama.cpp/discussions/13606)); (b) the authoritative failure analysis states that "a full-attention model has no checkpoint problem at all on llama.cpp, because its prefix KV can simply be truncated" ([particula.tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)); (c) mlx-lm's maintainers classify pure full-attention models as the working class, with MiniMax M2.5's 29s→3s warm-request speedup as the existence proof ([mlx-lm #980](https://github.com/ml-explore/mlx-lm/issues/980)); (d) MLA models are operationally mainstream on llama.cpp via the DeepSeek lineage with no cache-related issue class attached ([solarkyle conversion notes](https://huggingface.co/solarkyle/GLM-4.7-Flash-GGUF)). Section 6 gives the five-minute verification recipe to close the remaining gap empirically on Chronicle's own box before committing.

### 3.2 Known caveats, with mitigations

GLM-4.7-Flash is a **reasoning-capable model**, and Chronicle's design ("engine decides, LLM renders one grounded line") wants rendering, not deliberation. Thinking should be disabled via the chat template / reasoning budget — which also removes the main prefix-cache hygiene hazard of reasoning models: per-turn `<think>`-trace churn invalidating the matched prefix ([particula.tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)). The reported rare failure — an occasional thought fragment leaking at budget 0 — is cosmetic for dialogue rendering and detectable with a simple output filter ([HF discussion #44](https://huggingface.co/zai-org/GLM-4.7-Flash/discussions/44)).

Two operational notes from early adopters are worth carrying into the integration plan. First, sampling parameters matter: Z.ai recommends `temp 1.0 / top-p 0.95` for general use and `temp 0.7 / top-p 1.0` for tool-calling, with repeat penalty disabled and `--min-p 0.01` on llama.cpp ([unsloth guide](https://unsloth.ai/docs/models/tutorials/glm-4.7-flash)). Second, one user reported repetition loops past ~50K context on a Q8_0 quant; Chronicle's per-interaction prompts (shared prefix + short rider + few turns) sit far below that regime, but the roleplay feedback also notes the model mirrors repetitive user writing into deterministic outputs — a reason to keep NPC riders varied ([HF discussion #44](https://huggingface.co/zai-org/GLM-4.7-Flash/discussions/44)). Neither caveat touches the prefix-cache question; both are prompt-engineering concerns Chronicle's grounded-prompt design already controls for.

## 4. Fallback: Qwen3-30B-A3B-Instruct-2507

The fallback earns its slot on *certainty*, not novelty. Architecturally it is unimpeachable for this purpose: 48 layers of plain GQA full attention (32 query / 4 KV heads), 128 experts with 8 active, no hybrid anything, per the Qwen3 technical report ([arXiv 2505.09388](https://arxiv.org/html/2505.09388v1)). It is, in effect, the direct full-attention ancestor of the model being replaced — same vendor, same MoE sparsity class (30.5B total / 3.3B active), same chat-template ecosystem — so integration churn is near zero, and it is Apache 2.0 ([Qwen/Qwen3-30B-A3B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507)). Because the 2507 refresh is **non-thinking**, there is no reasoning trace to preserve or strip across turns, which removes the single most common self-inflicted cause of cache invalidation in agent harnesses ([particula.tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache)).

Capability is the honest trade-off: it is a mid-2025 model, and on raw reasoning it sits below both GLM-4.7-Flash and Qwen3.6-35B-A3B. But for *dialogue rendering* specifically its numbers are strong where it counts — Creative Writing v3: 86.0 (above GPT-4o-0327's 84.9 and DeepSeek-V3-0324's 81.6), Arena-Hard v2: 69.0, IFEval: 84.7 — and instruction-following is the property a "render this grounded intent" workload actually stresses ([Qwen3-30B-A3B-Instruct-2507 card](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507)). On throughput it is the fastest option evaluated: 35 tok/s on a 273GB/s M4 Pro under MLX, 42 on M4 Max, 62 on M5 Max 64GB, putting the 307GB/s M5 Pro around ~38–40 tok/s — more than double the requirement ([llmcheck.net](https://llmcheck.net/benchmarks), [r/LocalLLaMA Qwen3 benchmarks](https://www.reddit.com/r/LocalLLaMA/comments/1kdsp4z/qwen_3_performance_quick_benchmarks_across/)). Its prefix-cache behavior is the reference case on both stacks: Qwen3 belongs to the "single attention type — supported, no special configuration" class in cache-layer documentation ([LMCache docs](https://docs.lmcache.ai/mp/hybrid_models.html)) and the full-attention working class on MLX ([mlx-lm #980](https://github.com/ml-explore/mlx-lm/issues/980)). If GLM-4.7-Flash disappoints in the harness for any reason — behavioral, licensing review, anything — this is a drop-in replacement with zero architectural risk and a known performance envelope.

Two reserve options are documented for completeness but not recommended. **Qwen3-32B dense** is full attention and a small quality step up from the 30B-A3B in some evaluations, but dense 32B decode on 307GB/s lands near the 15 tok/s floor (published: 25 tok/s on M5 Max, 45 on M4 Ultra ([llmcheck.net](https://llmcheck.net/benchmarks))) — an unnecessary risk when the MoE alternatives are faster *and* fit the budget more comfortably. **Mistral Small 3.2 24B** is confirmed full-attention GQA and runs ~31–33 tok/s on Max-class chips, but its capability tier is a clear step below both picks for creative dialogue ([LLM Architecture Gallery](https://sebastianraschka.com/llm-architecture-gallery/attention-mechanism-distribution/), [llmcheck.net](https://llmcheck.net/benchmarks)). Either works mechanically if both primary picks fail validation; neither should be plan A or B.

## 6. Implementation and verification recipe

Serve with **llama-server** as the primary stack (most mature path for both picks on Metal), with mlx-lm's server as the alternative. The Chronicle-specific configuration: run with prompt caching defaults (`--cache-prompt` is already on), add `--cache-reuse 256` so near-miss prefixes get KV-shifted instead of re-prefilled, keep `-sps` at its default for similarity-based slot assignment, size slots to the expected number of concurrently "hot" NPC conversations, and use `--slot-save-path` + the `/slots/{id}?action=save|restore` endpoints if warm state must survive server restarts ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [tutorial #13606](https://github.com/ggml-org/llama.cpp/discussions/13606)). Two harness rules are non-negotiable regardless of model: the shared prefix must be **byte-stable** — no timestamps, UUIDs, or reordered tool definitions injected at the top, since matching is exact-prefix ([Tuning llama-server on Apple Silicon](https://medium.com/@michael.hannecke/tuning-llama-server-on-apple-silicon-9b3e778ab100)) — and prompt structure must keep the stable parts first (world rules → cell state → rider → turns), which Chronicle's design already does.

Verification takes five minutes and should be run on the actual Mac mini before the decision is locked: start the server at trace verbosity (`-lv 4`), send two requests sharing the long world-rules prefix with different riders, and read the `timings.cache_n` field in each response — a healthy run shows `cache_n` ≈ the shared prefix length on request two and a flat TTFT, while any `forcing full prompt re-processing` line in the log is the disqualifying signal ([particula.tech](https://particula.tech/blog/prompt-reprocessing-swa-hybrid-models-kv-cache), [server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). Pin the llama.cpp build in the run notes once verified — the 2026 track record on bleeding-edge model support argues for treating server upgrades as a deliberate, re-verified event rather than a habit ([Tuning llama-server on Apple Silicon](https://medium.com/@michael.hannecke/tuning-llama-server-on-apple-silicon-9b3e778ab100)). If GLM-4.7-Flash passes this check, adopt it; if it fails or misbehaves, rerun the same recipe against Qwen3-30B-A3B-Instruct-2507 and ship that.

## 7. Bottom line

The CUDA-bake-off-era model pick did not survive contact with the serving stack, and the fix is a model swap, not a workaround: no flag, fork, or checkpoint cadence makes hybrid prefix caching work on llama.cpp or MLX today, and vLLM/SGLang are the wrong engines for a 64GB Mac mini. **Adopt GLM-4.7-Flash** as the conversation-tier model (full-attention MLA, best-in-class capability, both stacks supported, throughput bar cleared), hold **Qwen3-30B-A3B-Instruct-2507** as the zero-risk fallback (proven, fast, non-thinking, Apache 2.0), and treat Gemma-4-26B-A4B as conclusively eliminated — it fails the architecture requirement and separately fails cache reuse on llama.cpp through its shared-KV design. The one piece of evidence no public source yet provides — a model-specific `cache_n` trace for GLM-4.7-Flash — is a five-minute local check (§6), and the fallback exists precisely so that even a surprise there costs one afternoon, not an architecture.
