# Verifying Chronicle's KV-Cache Prefix-Reuse Assumption for llama.cpp and MLX on Apple Silicon

**Date:** 2026-08-31
**Method:** 1 external research pass (Claude web), commissioned to verify/correct a specific
architectural claim in `docs/design/conversation-tier-design-notes-2026-08-30.md` §4 — that
"llama.cpp/MLX need explicit per-location warm cache files" for shared-prefix reuse, unlike
vLLM/SGLang's automatic prefix caching — against llama.cpp/MLX primary sources (GitHub
PRs/issues, official docs, model cards, one preprint). See
`notes/deep-research-prompts-2026-08-31.md`, Prompt 40.

---

## TL;DR
- **The internal doc's claim is now partly WRONG and stale: llama.cpp does NOT require "explicit per-location warm cache files."** Its `llama-server` performs automatic longest-common-prefix KV reuse in-slot (`cache_prompt`, default true), automatic cross-request/cross-slot prefix reuse via host-RAM prompt caching (`--cache-ram`/`-cram`, default 8192 MiB, PR #16391, enabled by default since October 2025), and chunk-level shifted reuse (`--cache-reuse N`). Explicit save/restore files (`/slots?action=save|restore`, `llama_state_save_file`) still exist but are now a deterministic fallback, not the required path. MLX's `mlx_lm.server` also does automatic in-memory longest-prefix reuse (`LRUPromptCache`), though the *disk* save/load path is more hand-rolled.
- **But for Chronicle's specific target model this barely matters: Qwen3.6-35B-A3B is a hybrid Gated-DeltaNet/recurrent MoE, and automatic prefix caching is broken for hybrid/recurrent models on BOTH stacks today.** llama.cpp logs "forcing full prompt re-processing due to lack of cache data (likely due to SWA or hybrid/recurrent memory)" every turn; mlx-lm issue #980, titled "Prefix cache reuse is broken for all hybrid-architecture models (sliding window, SSM/Mamba)," confirms the recurrent state "can't be split at an arbitrary token boundary." The llama.cpp fix (issue #22384) lives only in forks, not upstream master, as of Aug/Sep 2026.
- **Recommendation: build on `llama.cpp`'s `llama-server` (automatic prompt caching + explicit `/slots` save/restore as a deterministic fallback), but validate cache behavior against the *exact* model build first, and strongly consider a pure full-attention model (or a dense Qwen/Llama) for the NPC "rider" workload so prefix caching actually works.** Do not architect around manually managing one warm-cache file per location — that is a fallback, not the primary mechanism, and it is defeated by the hybrid architecture anyway.

## Key Findings

### 1. llama.cpp KV-cache save/load and automatic reuse — CONFIRMED, with important nuance
- **Explicit state files exist.** `--prompt-cache FNAME` (CLI), the `/slots/{id}?action=save|restore` HTTP endpoints (require `--slot-save-path`), and the C API `llama_state_save_file`/`llama_state_load_file` all persist full sequence KV state to disk. The official tutorial (Discussion #13606) shows `restore_ms: 0.739` to restore a 72-token slot (`n_read: 7669224` = 7.67 MB) — i.e., the disk-read/deserialize step only, not prefill.
- **Automatic in-slot reuse is default.** `cache_prompt: true` (default) reuses the common prefix within a slot; only the differing suffix is prefilled. Partial/longest-prefix reuse is automatic within a slot.
- **Automatic cross-request/cross-slot reuse now exists.** PR #16391 ("server: host-memory prompt caching," authored by ggerganov, merged October 2025; CLI `--cache-ram`/`-cram`, default 8192 MiB). In the maintainer's own words: *"The host-memory prompt cache acts as 'extra slots' with which we can calculate prefix similarity and decide to hot-swap them into the llama_context if it would reduce the processing. The cache is stored in regular RAM."* `--cache-idle-slots` (default enabled) saves idle slots into that cache. Reported benefit: up to 93% time-to-first-token reduction for cached prefixes (Jesse Quinn, "Understanding --cache-ram in llama.cpp"). This is the vLLM-like behavior the doc assumed llama.cpp lacked.
- **`--cache-reuse N`** enables reuse of a matching chunk of ≥N tokens via KV shifting even when the shared content is not a pure leading prefix (e.g., RAG passages that move).
- **Constraints:** reuse is token-match based; slot selection uses LCP similarity (`-sps`, default 0.5) and is imperfect (picks a "sufficient" match by LCP similarity, not necessarily the optimal longest-prefix match — confirmed by user reports in Discussion #13606). Slots are finite; the classic "10 slots, 11 cyclic prompts" case evicts. On Apple Silicon unified memory, `--cache-ram` competes with the active KV cache for the same pool.

### 2. MLX save/restore/reuse — CONFIRMED as first-class in-memory, more hand-rolled on disk
- **`mlx_lm.cache_prompt`** writes a `.safetensors` prompt-cache file; **`mlx_lm.generate --prompt-cache-file`** treats it as a prefix. Python API: `make_prompt_cache`, `save_prompt_cache`, `load_prompt_cache`, `trim_prompt_cache`.
- **`mlx_lm.server` has automatic in-memory longest-prefix reuse** via `LRUPromptCache` (in `mlx_lm/models/cache.py`), reporting `cached_tokens` in the usage block, bounded by `--prompt-cache-size`/`--prompt-cache-bytes`. So MLX is NOT purely "hand-roll it yourself" for the in-memory case — the LRU implementation does longest-prefix matching and, where the cache layer is trimmable, trims a longer cached entry down to the reusable boundary.
- **Disk persistence across restarts** was only recently added (PR #1405, `--prompt-cache-dir`); base `mlx_lm.server` lost its cache on restart. Reported warm-vs-cold restart benchmark from that PR: M2 Ultra cold prefill 1955.19 ms → warm 209.42 ms (89.3% drop); M3 Max 4834.93 ms → 289.86 ms (94.0% drop).
- Alternative MLX servers with multi-slot disk KV cache: **mlx-textgen** (multiple on-disk KV-cache slots that don't overwrite each other — explicitly pitched for agentic workflows), **LM Studio's mlx-engine** (256-token-boundary disk checkpoints, restores longest available cached prefix), **vllm-mlx**.

### 3. A server that does automatic longest-common-prefix reuse (vLLM-like) — YES, several
- **llama.cpp `llama-server`** itself now does this (host-memory prompt cache + `--cache-reuse`), so the caller does NOT have to manage explicit warm-cache files per location for full-attention models.
- **vllm-mlx** (waybarrios/vllm-mlx) is an explicit vLLM-style Apple Silicon server: continuous batching, paged KV cache, automatic prefix cache, SSD-tiered cache, OpenAI + Anthropic APIs in one process. Per the project's paper (arXiv 2601.19139, "Native LLM and MLLM Inference at Scale on Apple Silicon," EuroMLSys '26): *"we achieve 21% to 87% higher throughput than llama.cpp across models ranging from Qwen3-0.6B to Nemotron-30B … text prefix caching achieves 5.8x speedup on shared prompt prefixes,"* with up to 525 tokens/sec on an Apple M4 Max. (These are the project's own benchmarks — treat as vendor data.)
- **mlx_lm.server** does automatic longest-prefix in-memory reuse.
- This changes the architecture from "we manage cache files per location" to "the server just does it" — **for full-attention models.**

### 4. The hybrid-model landmine (decisive for Qwen3.6-35B-A3B)
- **Qwen3.6-35B-A3B is a hybrid sparse MoE.** Per the Hugging Face model card: *"35B in total and 3B activated … Number of Layers: 40 … Hidden Layout: 10 × (3 × (Gated DeltaNet → MoE) → 1 × (Gated Attention → MoE)) … Number of Experts: 256 … 8 Routed + 1 Shared … Context Length: 262,144 natively and extensible up to 1,010,000 tokens."* Released April 15, 2026 under Apache 2.0. It is emphatically NOT a pure full-attention transformer — 3 of every 4 layers are recurrent Gated DeltaNet.
- **llama.cpp:** hybrid/recurrent models force full prompt re-processing every turn ("forcing full prompt re-processing due to lack of cache data (likely due to SWA or hybrid/recurrent memory)"). Root cause (issues #20225, #22384): the checkpoint search uses `cur.pos_min < pos_min_thold`, but for recurrent models `pos_min` always equals the full sequence length, so the check always fails and no checkpoint is restored; additionally checkpoint creation requires ≥64 tokens. The proposed fix (use `cur.pos_max <= pos_next` for recurrent/hybrid models, lower the threshold to 4 tokens) exists only in forks (buun-llama-cpp), **NOT merged to upstream master** as of Aug/Sep 2026. Issue #24055 (open) and #24587 (Aug 2026) confirm it remained broken/regressed; a regression was even bisected to commit e98cb51 (working on build b9309, broken on b9354). Recurrent state also cannot be partially truncated, so partial-prefix reuse fundamentally can't work the way it does for full attention.
- **MLX:** issue #980 — "Prefix cache reuse is broken for all hybrid-architecture models (sliding window, SSM/Mamba)." The Mamba/SSM/DeltaNet state "is a compressed recurrent state that can't be split at an arbitrary token boundary." As of March 2026 the issue reports MiniMax M2.5 as about the only major model where MLX prefix caching worked correctly. LM Studio's mlx-engine explicitly disables cross-turn caching for its hybrid VisionModelKit path for the same reason.

### 5. Latency reality on Apple Silicon
- **Restore-from-disk vs recompute-from-scratch is a large win — for full-attention models.** The single-author preprint "Agent Memory Below the Prompt" (Yakov Pyotr Shkolnikov, arXiv:2603.04428v1, 17 Feb 2026, measured on an M4 Pro) reports, verbatim: *"Context restoration drops from 15.7 seconds to 577 ms (warm, disk) or 719 ms (hot, memory) at 4K context on Gemma 3 12B … cache restoration reduces time-to-first-token by up to 136× (Gemma: 22–136× at 4K–32K)."* Restore disk I/O itself is ~5–80 ms; the ~500 ms reload "hides behind the previous agent's decode phase."
- **No large-prefix `restore_ms` figure is published for llama.cpp** — only the 72-token/0.739 ms example. A multi-thousand-token slot is hundreds of MB on disk (the 72-token slot was already 7.67 MB); plan to measure your own prefix sizes.
- llama.cpp's on-Apple-Silicon reality: one `llama-server` with correctly-set `--parallel`/`--batch-size`/`--ubatch-size` outserves most multi-process setups; `--cache-ram` competes with active KV in unified memory (the default 8192 MiB can starve KV on a 64 GB box).

## Details

**On the doc's exact wording.** The claim "vLLM block-hash prefix caching, SGLang radix tree do this automatically; llama.cpp/MLX need explicit per-location warm cache files" is stale on two counts. (1) llama.cpp gained automatic host-memory prefix caching in October 2025 (PR #16391); it now calculates prefix similarity against cached prefixes and hot-swaps them, conceptually similar to (though less sophisticated than) vLLM's block-hash APC or SGLang's radix tree. (2) `mlx_lm.server` has had an automatic in-memory LRU longest-prefix cache. So "need explicit per-location warm cache files" is no longer accurate as a blanket statement — explicit files are a deterministic fallback (useful when you want guaranteed pinning to a slot), not the only mechanism.

**Where the doc is still directionally right.** Neither llama.cpp nor MLX matches vLLM/SGLang in sophistication. llama.cpp slot selection is LCP-similarity-based and imperfect; the cache is per-slot / per-cache-ram-budget and evicts; there is no global radix tree spanning all requests. If you need deterministic, guaranteed reuse (e.g., pin "world rules + location X" to a known slot), the explicit `/slots` save/restore path is still the reliable lever — which is exactly the "warm cache file per location" pattern, just no longer mandatory.

**MoE and Apple Silicon fit.** A ~35B-total / ~3B-active MoE at 4-bit (~20–25 GB weights) fits comfortably on a 64 GB M5 Pro Mac mini with room for KV slots and prompt cache; the model even runs on 24 GB Macs in 4-bit GGUF. The problem is not memory — it's that the hybrid/recurrent attention breaks the prefix-reuse mechanism Chronicle's whole design depends on.

**Known-good stacks other Apple-Silicon setups use.** For single-process multi-request serving on Apple Silicon, the two mainstream choices are (a) `llama.cpp` `llama-server` with `--parallel N --cont-batching --cache-ram --cache-reuse` (GGUF), and (b) `mlx_lm.server` (OpenAI-compatible, continuous batching). For explicit vLLM-like behavior, `vllm-mlx` and LM Studio's `mlx-engine` are the emerging options; `mlx-textgen` is notable for multi-slot on-disk KV caches aimed at exactly the agentic/multi-prefix pattern Chronicle has. llama.cpp generally leads on raw single-stream throughput; MLX-based stacks lead on sustained generation throughput in some benchmarks.

## Recommendations

1. **Do NOT architect around "one manually-managed warm-cache file per location."** That was the doc's premise; it is a fallback mechanism today, and it is defeated by the hybrid model anyway. Plan on the server's automatic prompt caching as the primary path.

2. **Primary implementation: `llama.cpp` `llama-server`.** Launch with `--parallel N`, `--cont-batching`, `-cram` (tune *below* the default 8192 MiB on a 64 GB box to avoid starving KV), `--cache-reuse 256`, `--flash-attn`. Rely on `cache_prompt: true` for automatic in-slot prefix reuse and host-RAM caching for cross-request reuse. Keep the explicit `/slots?action=save|restore` (`--slot-save-path`) path available for deterministic per-location pinning of the stable "world rules + location" prefix if automatic slot selection proves flaky. Concrete API surface: `POST /slots/{id}?action=save` / `?action=restore` over HTTP, or `llama_state_seq_save_file`/`llama_state_seq_load_file` in-process.

3. **Resolve the model-architecture blocker before committing — this is the single highest-leverage decision.** Because Qwen3.6-35B-A3B is hybrid/recurrent (3-of-4 layers Gated DeltaNet), verify on your *exact* build whether context-checkpoint restore works — watch the server log for "forcing full prompt re-processing due to lack of cache data." If it re-prefills every turn (the current expected behavior on upstream master), either (a) switch to a pure full-attention model of comparable quality (a dense ~14–32B, or a non-hybrid MoE) so prefix caching works, or (b) pin to a fork/build where the hybrid checkpoint fix (issue #22384) is present and validated. This determines whether Chronicle's "pay prefill only for the rider" premise holds at all.

4. **Structure the prompt for maximal prefix stability.** Keep the order world-rules → location/cell → per-NPC rider → turns, and ensure nothing volatile (timestamps, RNG, reordered tool lists) contaminates the shared prefix — any such contamination silently invalidates the cache. For an agent with a stable prefix, `cached_tokens`/`cache_n` should approach the prefix length on every request after the first.

5. **Benchmark restore vs recompute on the real hardware.** There is no published large-prefix `restore_ms` for llama.cpp; measure `save_ms`/`restore_ms` for your actual prefix sizes and compare against cold prefill. Expect large wins (the arXiv M4 Pro data suggests 20–130×) *only if the model supports partial reuse.*

**Benchmarks/thresholds that change the recommendation:** If `cached_tokens`/`n_past` shows the shared prefix is reused each turn (cache_n ≈ prefix length), stay on llama-server auto-caching and skip explicit files entirely. If the log shows full re-processing every turn on the hybrid model, switch models or move to a fork with the merged fix. If throughput/concurrency needs exceed what one llama-server's slot count delivers, evaluate `vllm-mlx` for paged-cache continuous batching.

## Caveats
- **Version drift is the dominant risk.** llama.cpp cache behavior has changed repeatedly through 2026 (PRs #16391, #22929, #24176, #25472; regressions in #15082, #24055). Pin a build and re-test after every upgrade.
- **The hybrid-model fix status is fluid.** As of Aug/Sep 2026 no upstream-merged llama.cpp PR definitively fixes DeltaNet/recurrent checkpoint restore; this could change — re-check issue #22384 and its linked PRs before finalizing model choice.
- **Some latency figures come from a single-author, non-peer-reviewed preprint** (arXiv:2603.04428, "Agent Memory Below the Prompt") and vendor sources (LM Studio blog, jessequinn.info, vllm-mlx's own paper) — treat as directional, not authoritative. The M4 Pro numbers do not transfer directly to an M5 Pro Mac mini.
- **vllm-mlx maturity:** it is a young project (described as "bus factor 1" by one independent reviewer); its own benchmarks show throughput leads but third-party testing also reported FP16 memory-exhaustion failures at 16K context.
- **Unified-memory contention:** on a 64 GB Mac mini, the default 8192 MiB `--cache-ram` plus model plus KV slots can trigger "failed to find free space in the KV cache" errors; size the cache deliberately rather than accepting defaults.
