# Native BarterMenu / Vendor-Price Hooking in Skyrim SE/AE: Landscape, Safe Patterns, and Conflict Risks for "Chronicle"

## TL;DR
- **You are almost alone in vtable-patching `RE::BarterMenu` for pricing, but not alone in altering vendor prices at the native level.** The dominant maintained economy mods (Trade & Barter, Trade Routes, Gilded Road) are Papyrus/ESP/keyword-driven, not native hooks — but two active SKSE frameworks, JerryYOJ's **Dynamic Prices Framework** and shazdeh2's **Dynamic Pricing Framework**, do modify displayed barter prices from native C++, and they are the mods most likely to collide with Chronicle.
- **Overwriting a vtable slot with a raw function-pointer write is the single most dangerous part of your design.** If any other plugin writes the same slot, whoever writes last wins and the earlier hook is silently lost. The community-standard fix is to *capture and call through* the previous pointer (which `REL::Relocation::write_vfunc` returns), so hooks form a chain instead of clobbering each other.
- **Recommendation: don't own the BarterMenu vtable slot yourself.** Either (a) become a *consumer* of Dynamic Prices Framework's callback API instead of installing your own hook, or (b) if you keep your own hook, always store and invoke the returned original pointer, install late (`kDataLoaded`/`kPostPostLoad`), and publish your vtable offset so others can detect you. This eliminates the "one silently overwrites the other" failure mode.

## Key Findings

### (1) Other mods touching BarterMenu / vendor prices
- **Trade & Barter (kryptopyr), Nexus SSE #23081** — *Papyrus/ESP only, no native hook.* The author states verbatim: "I've designed this to be a very lightweight mod. It uses a series of carefully conditioned perks to accomplish nearly all of it's changes. The only script included in the mod is the MCM script that controls the menu options, so the mod will not cause any performance hit or save game bloat." Its price changes work by altering the `VendorGold...` and `PerkInvestor...` leveled lists that determine merchant base gold. It requires SKSE only for the SkyUI MCM. **No BarterMenu vtable interaction; near-zero direct crash risk with Chronicle** — but note the page's own warning: "If Trade & Barter is loaded last, then it will overwrite any changes made by other mods to these leveled lists," and its multipliers stack in-world with Chronicle's markup.
- **Trade Routes – Regional Economy SE (Nexus SSE #12358)** — *Papyrus + ESP*, requires SKSE64 2.0.15+ but only for script functionality; it dynamically rewrites gold values via scripts and leveled lists, not via a native BarterMenu hook.
- **The Gilded Road (Nexus SSE #169528)** and **Immersive Merchants (Nexus SSE #156053)** — *Not native hookers themselves*; they are **content/config mods that depend on shazdeh2's Dynamic Pricing Framework.** Gilded Road's requirements list names it verbatim: "Dynamic Pricing Framework (by shazdeh2) - The core brain of the mod." The native hooking is done by the framework, not these mods.
- **Dynamic Prices Framework (JerryYOJ, Nexus SSE #144874, source on GitHub `JerryYOJ/DynamicPrices-SKSE`)** — *Native SKSE/CommonLibSSE-NG hook into the trader pricing/item-card path.* Description, verbatim: "This mod hooks into the pricing system of traders and provides a way to register a callback to modify the price on each item." Developers must "declare an dll exported function with `extern \"C\" __declspec(dllexport)`" whose signature is `(RE::Actor* trader, RE::InventoryEntryData* objDesc, uint16_t a_level, RE::GFxValue& a_updateObj, bool is_buying)` and which "must return a float representing the price multiplier." The presence of `RE::GFxValue& a_updateObj` strongly indicates it hooks the **item-card / Scaleform value-update path** (the same "AdvanceMovie item-card injection" family used by SkyrimSouls and Smithy Info), i.e. it rewrites the price value pushed into the UI. **This is functionally the closest existing analog to Chronicle and the most important compatibility target.**
- **Dynamic Pricing Framework (shazdeh2, Nexus SSE #167487, source `shazdeh/Dynamic-Pricing-Framework`)** — *Native CommonLibSSE-NG plugin*, a separate implementation, adjusts buy/sell prices by keyword + conditions via JSON. Per its Nexus page, "Since 1.0.2 in Barter menu you'll be able to see which items are cheaper or more expensive than usual, they are highlighted with an indicator, this is compatible with all UI mods, and can be customized or completely turned off via the config json file." Supports SE/AE/VR. This is a second independent native price modifier.
- **Barter Limit Fix (powerofthree/KernalsEgg, Nexus SSE #77173)** and **kassent/BarterFix** — native SKSE plugins, but they fix the 32,767-gold selling bug ("Fixes a bug that can prevent the player from receiving gold when selling to a merchant if the merchant has more than 32,767 gold"); they touch barter *transaction* code, not the displayed price computation, so overlap with Chronicle is minimal.
- **BestInClass++ (Dakraid)** — native plugin that "hooks the appropriate function" and injects into the Barter and Container menus, but for best-in-class markers, not pricing.
- **Inventory Interface Information Injector / "I4" (Parapets & Jelidity, Nexus SSE #85702)** — native SKSE plugin that hooks the item-list update path (its crash logs reference `Hooks::IconSetter::ProcessListFunc`) shared by inventory/barter/container menus. It "is a framework that makes it possible to manipulate the information that appears in SkyUI's item menus, as well as inject new icon art," with configs in `SKSE\Plugins\InventoryInjector`; per its docs, "if there are any conflicts between them, the later-loading config will take priority." It does not change prices, but it hooks the *same UI update machinery* Chronicle's PostCreate/item-card path is adjacent to, and it is nearly universal in modern load orders — making it the single most important coexistence target after Dynamic Prices Framework.

### (2) Known-safe pattern for multiple plugins hooking the same slot
- **CommonLibSSE-NG's `REL::Relocation<T>::write_vfunc(offset, newFn)` returns the previous function pointer.** The canonical, safe idiom (seen across EngineFixes, Particle Wind, and many po3 plugins) is: `_original = vtbl.write_vfunc(0xNN, Hook);` and then **call `_original(...)` inside your hook**. If every plugin does this, hooks chain: each runs its logic and passes control to the pointer it captured (which may be another mod's hook, not just the vanilla function). Chronicle *must* do this rather than blind-writing the slot.
- **For call-site/inline hooks, the community convention is the SKSE `Trampoline`** (`SKSE::AllocTrampoline(n)` + `trampoline.write_call<5>(addr, Hook)` / `write_branch`). Because each plugin allocates its own trampoline and the trampoline preserves and returns the displaced original call target, two plugins hooking the *same call site* also chain rather than clobber — the well-known failure mode there is trampoline *exhaustion* (allocation failure, e.g. the "Trampoline.h: Failed to handle allocation request" error), not silent overwrite.
- CommonLibSSE-NG also exposes `stl::write_vfunc` / `stl::write_thunk_call` and a `detour_vfunc` helper (used by Community Shaders' hook system) that wrap the same capture-and-chain semantics.
- **`RE::VTABLE_BarterMenu`** exists as a documented address set in CommonLibSSE-NG, and `RE::BarterMenu` exposes `PostCreate`, `PostDisplay`, `ProcessMessage`, `Accept`, etc., as virtual functions — so vtable-slot hooking of BarterMenu is a supported, addressable operation. A Fallout 4 analog (shad0wshayd3's BakaInterface) shows the exact idiom for barter: `_BarterMenu__Call = targetVTBL_0.write_vfunc(0x01, ...)`, capturing the original before overwriting.
- **Load-order/timing convention:** install UI/menu hooks late — at `kDataLoaded` or `kPostPostLoad` — precisely "to ensure all SKSE plugins are loaded and can co-exist with other" menu-modifying plugins (Community Shaders documents this rationale). Whoever installs last on a raw write wins, so late, chained installation is the safe combination.

### (3) Documented crashes / price conflicts between native barter plugins
- There is **no widely-documented, confirmed crash report of two pricing plugins both vtable-patching BarterMenu** — largely because Chronicle's specific approach (owning the BarterMenu PostCreate slot for pricing) is rare. Dynamic Prices Framework and Dynamic Pricing Framework are the only close analogs, and each expects to be the sole native price modifier of its type.
- The closest real-world evidence of the *class* of failure is on the shared item-list update path: SkyUI's bug/posts threads show CTDs whose crash logs implicate **`Hooks::IconSetter::ProcessListFunc`** (Inventory Interface Information Injector) during menu updates on downgraded/mismatched runtimes — a native menu-list hook implicated in menu crashes. This demonstrates that native hooks on the barter/inventory list machinery are a documented crash surface when versions or hook order go wrong.
- Both frameworks warn implicitly about collision at the *config* level ("just don't name it the same as others or they'll override"), and I4's docs note that when configs conflict "the later-loading config will take priority" — the same last-writer-wins semantics that, at the native vtable level, would silently disable an earlier hook.

## Details

**Why Chronicle's design is fragile.** Writing a function pointer directly into `RE::BarterMenu`'s vtable slot for `PostCreate` mutates a process-global table. Every `BarterMenu` instance dispatches through that one table, so the *last* plugin to write the slot at load time is the only one whose function is reachable; earlier writers are not "merged," they are overwritten and their code never runs. Unlike ESP record conflicts (resolved by load order in a predictable, visible way) or Papyrus (where multiple scripts can independently `SetActorValue`), a raw vtable write is invisible to mod managers and to LOOT, so users get "my markup mod stopped working" with no error.

**The fix is intrinsic to CommonLibSSE-NG.** `write_vfunc` deliberately returns the old pointer so you can chain. If Chronicle stores that pointer and calls it, then a second pricing mod that also chains will still run — control flows Chronicle → (previous hook, possibly another mod) → vanilla `PostCreate`. This converts "silent overwrite" into "cooperative chain." The only remaining subtlety is *price-stacking order*: if two mods both multiply the displayed price, the result is order-dependent (Chronicle's social-standing multiplier × another mod's regional multiplier), which is usually acceptable but should be documented.

**The better architecture: consume, don't hook.** JerryYOJ's Dynamic Prices Framework already solved this exact problem generically: it installs the single native hook, and every price mod registers a `float`-returning multiplier callback via JSON (`{"NativeCallbacks":["Chronicle.dll!GetChronicleMultiplier"]}`). Because callbacks return a *multiplier* (not an absolute price), multiple registered callbacks are designed to be combined/stacked rather than one-wins, so Chronicle's social-standing logic could ship as a callback with **zero** vtable patching and automatic compatibility with Gilded Road, Immersive Merchants, and any other consumer. This is the lowest-risk path and is worth strong consideration even though it adds a dependency.

**Caveat on source verification.** I confirmed both frameworks exist as CommonLibSSE-NG C++ plugins with `src/`/`include/` trees and confirmed JerryYOJ's callback signature and "hooks into the pricing system of traders" description verbatim from the Nexus page. I was **not** able to open the raw `.cpp`/`.h` files to quote the exact `write_vfunc` offset, Address Library `RelocationID`, or the callback-combination loop; the item-card/GFxValue hook target and multiplier-stacking behavior are strong inferences from the public API surface, not verified from source lines.

## Recommendations

1. **Stage 1 — Immediately make your hook chain-safe.** Replace any blind vtable write with `_originalPostCreate = vtbl.write_vfunc(<PostCreate offset>, Chronicle_PostCreate);` and unconditionally call `_originalPostCreate(...)` at the appropriate point in your hook. This one change removes the "silently overwrites the other" defect regardless of what else you do.
2. **Stage 2 — Install late and defensively.** Register your hook at `kDataLoaded` (or `kPostPostLoad`) rather than at plugin-load, so you chain on top of whatever else is present, and guard the memory write with correct page-protection handling (CommonLibSSE-NG does this for you via `write_vfunc`).
3. **Stage 3 — Prefer the framework path.** Evaluate shipping Chronicle's markup as a **Dynamic Prices Framework callback** instead of a self-installed hook. If you adopt it, you inherit tested multi-mod stacking and drop your vtable dependency entirely. Keep your own hook only if you need behavior the callback signature can't express (e.g., you must alter `PostCreate` layout, not just the price value).
4. **Stage 4 — Test the concrete conflict matrix.** Before release, run barter menus with, in combination: Dynamic Prices Framework + a consumer (Gilded Road), Dynamic Pricing Framework (shazdeh2), Inventory Interface Information Injector/I4, and SkyUI. Watch specifically for CTD on barter-menu open and for your markup silently not applying (the signature of a lost hook).
5. **Benchmarks that change the plan:** If testing shows your hook is being overwritten (markup absent when another price mod is present), that confirms you must chain and/or move to the framework. If you see CTDs only with I4/SkyUI present, the problem is item-list update timing/offset, not pricing — install later and verify AE-vs-SE offsets. If prices come out wildly wrong with another multiplier mod, the issue is stacking order, which you resolve by documenting or by reading the current price value rather than re-multiplying a base.

## Caveats
- Chronicle's exact technique (owning `BarterMenu::PostCreate` for pricing) has **no exact public precedent**, so there is no ready-made compatibility report for "two mods both hook BarterMenu PostCreate." My conflict analysis is built from the mechanism (global vtable = last-writer-wins) plus the closest analogs (Dynamic Prices/Pricing Frameworks; I4's `ProcessListFunc`), not from a documented head-to-head crash.
- I could not verify the frameworks' internal hook offsets or callback-combination code from source; treat the "item-card/GFxValue hook" and "multipliers stack" claims as high-confidence inferences, not confirmed code reads.
- Native hooks are tightly bound to game/SKSE version; several of the mods cited (Barter Limit Fix, kassent/BarterFix) target specific runtimes, and address offsets differ between SE 1.5.97 and AE 1.6.x — any BarterMenu vtable offset you use must be resolved through Address Library for all runtimes you support.
- Trade & Barter and Trade Routes change prices through perks/scripts/leveled lists, so they will *co-exist* with Chronicle at the code level but their effects **stack in-world** with your markup; that is a balance concern, not a crash concern.
